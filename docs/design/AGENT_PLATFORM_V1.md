# Stardust Agent 平台：用一个大创项目跑通第一版

状态：实施提案。首页定位提交 `ae00896` 改了介绍文案。本文的 Agent 注册、统一运行接口和版本化预审报告是拟开发功能；现状依据本地工作区及本地跟踪的 `origin/main`（`74ce0a9`），不代表线上验收结果。

## 首版服务谁

学生在一个项目里完成申报，教研团队维护可供调用的 Agent。第一版让两个职责不同的 Agent 处理同一个大创项目：申报助理协助起草，材料预审助理检查学生选定的草稿。现有 35 个 Skills 继续提供不同赛道的写作规范、范例结构和模板。

学生登录后仍以项目为入口，首页不要求挑选 Agent。先说“我想申报大创，已有学校通知和去年草稿”，核对资料后和申报助理修改研究方案。保存一版正文，再点“检查这版草稿”。预审结果单独存入项目；每条问题指向章节，能找到依据时列出来源，资料不足时说明还缺什么。学生次日回来能看到检查的是哪一版、改过哪些地方，再决定是否重新检查或导出 Word。

## 最小平台约定

| 对象 | 第一版需要记录什么 |
| --- | --- |
| **项目** | 复用现有项目、账号归属、确认过的资料和章节。多个 Agent 在同一项目内工作，调用另一个 Agent 不会更换赛道。 |
| **Agent 定义** | 稳定的 ID、发布版本、职责、适用场景、允许的工具、输入和预期产物。首版只加载维护者提交的定义，引用已注册的执行器。 |
| **运行 Run** | 一次明确的任务：项目、发起人、Agent 版本、输入版本、请求去重键、状态、进度和结果引用。一个项目可以有多次运行。 |
| **产物 Artifact** | 一份可重新打开的结果：章节草稿、预审清单或导出文件。记录产物版本、来源运行、所依据的正文版本；文件可引用原有存储。 |

例如，预审助理的定义可以长这样。这是拟定的配置格式，现有服务尚不会加载它：

```json
{
  "id": "proposal-reviewer",
  "version": 1,
  "supported_skills": ["innovation-research"],
  "executor": "review_saved_draft",
  "input": "saved_draft_snapshot",
  "tools": ["check_draft_snapshot"],
  "output": "review_report"
}
```

`review_saved_draft` 和 `check_draft_snapshot` 均为拟新增接口。将现有 `validate_project` 中可复用的规则抽出来，让检查工具接收选定的草稿快照，避免排队期间正文已改、报告却挂在旧版本上。每条意见至少有章节、发现的问题和建议；涉及学校要求时附依据，资料不足时标为待核对。执行器只读获准使用的资料和指定草稿，可以新增报告，不能修改正文或确认事实。结构检查先用规则完成；需要模型解释时再走现有模型与计费入口。

## 三个可单独交付的改动

1. **注册两个 Agent，复用一个项目。** 新增 Agent 目录，将申报助理接到原有聊天服务，将预审助理接到单独的检查执行器。目录可由 `GET /api/agents` 提供。沿用原来的登录、免费额度和计费；从会话身份确定资料范围，服务端在调用工具时再次检查权限。验收：同一项目可分别起草和检查，预审不能改正文；原有聊天入口照常可用。
2. **让一次预审产生可以找回的结果。** 拟新增 `POST /api/projects/{id}/runs`，接收目标、Agent 和正文版本，返回 `run_id`；`GET /api/projects/{id}/runs/{run_id}` 返回状态和产物。提交时绑定输入快照。Vercel 接收请求并检查项目归属，沿用现有云端项目存储，长任务交给独立云端 worker。页面对同一次提交复用请求键；服务端在账号、项目内去重，相同键对应不同输入时返回冲突。付费调用结果不确定时先核账。验收：刷新后能打开同一份报告；正文更新后旧报告仍指向旧版；重复提交不会执行或收费两次，其他账号不能查询此任务或产物。
3. **把运行接进学生真正使用的页面。** 项目页提供“继续起草”“检查这版草稿”“查看上次结果”，显示进行中、需要补资料或已完成的任务。根据预审意见回到相应章节，修改后由学生决定再次检查或导出。再用“学校通知材料清单助理”验证扩展方式：复用已有执行器、工具和产物类型时，只加定义和验收样例即可进入同一工作台；需要新能力时再新增工具或渲染器。

第一个开发里程碑是**一个学生完成一次从起草到预审再到修改、导出的闭环**。内测记录多少个有草稿的项目成功拿到可用清单、清单中的意见能否定位和处理，以及完成一次任务的时间与成本。根据使用结果再扩展至挑战杯、奖学金等场景。

如果产品的第一批用户其实是**负责搭建 Agent 的老师或开发者**，则应把首个前台流程改为“从模板创建 → 选择可用工具 → 用样例试跑 → 发布指定版本给学生 → 可回滚”。这个产品仍需要同一套 Agent、Run 和 Artifact 约定；区别在于先交付创作者的发布流程，还是学生的申报流程。
