# 2026-10-18 事故复盘：内置模型突然不能用了

## 先说结果

线上（agent.stardust.website）用「平台预设」这套内置模型生成章节，会直接报错、生成不出来。这个问题从今天上午那次合并上线之后开始。现在代码侧已经修好，改在 `server/app.py`，相关单测 60 个全过。

需要说明的是，这不是模型本身坏了，是**我们自己的代码在后端把用户身份搞丢了**，导致内置模型这条链路在校验积分时直接失败。下面把过程原原本本写清楚。

## 用户看到的现象

用内置模型点「生成本章」，等一会儿就提示生成失败。换成自己填 API Key 的自定义模型、或者本机 Ollama，都正常。会话聊天（不是章节生成）也正常。也就是说，只有「内置模型 + 章节生成」这个组合挂。

这一点其实很关键，它把范围缩得很小：内置模型是唯一一条**要扣积分**的路径，其他两条都不走积分。

## 怎么定位到后端

顺着「只有内置模型挂」往下查，看的是这条链路：
前端带上 `provider: preset` 请求 → 后端 `generate_section` → 平台预设走 `_agent_for_config`，这里会给它挂一个积分计量器 `WorkbenchMeter`。

计量器在扣费前要确认「你是谁」，也就是要读用户身份。而身份是放在一个请求上下文变量 `request_identity` 里的，由鉴权中间件在请求进来时写进去。计量器在实际扣费时，最终走到 `SupabaseStore.reserve_workbench_usage`，里面有个 `_identity()`，如果读不到身份就直接抛 `PermissionError("需要先登录，才能访问项目数据。")`。

问题就出在这里：今天上午的 `08fb2e5` 这次提交，把章节生成从「请求里同步执行」改成了「丢到后台线程池执行」。而 Python 标准库的 `ThreadPoolExecutor` **不会把请求上下文带进新线程**。于是后台线程里读身份，读到的是空，计量器拿着一个假的 `local_user` 去扣费，`_identity()` 当场拒绝。

我实测确认过这一点：

```
主线程读身份   -> {'user_id': 'real_user_123', 'access_token': '...'}
后台线程读身份 -> None
```

再往上，`_metered_invoke` 只兜住了「积分不够」这类异常，没兜 `PermissionError`，异常一路冒出去，任务被标记成 failed，接口最后统一转成 500。

## 为什么只有内置模型受影响

自定义模型（BYOK）和本机 Ollama 这两条路，根本不经过积分计量器，也就不需要用户身份，所以照常能用。内置模型是唯一要扣积分的，刚好就踩中。现象和代码对得上，基本可以确定就是它。

## 前后端为什么会一起上线（你问的这点）

你这次提的 PR（#24、#25、#26）我逐条对过 diff，**确实只动了前端**，没碰后端。问题不在你的改动本身，而在分支合并的方式：

- 你的前端 PR #24（提交 `fd2326a`）的父提交是 `04ffa0f`，而 `04ffa0f` 是一条后端改动，不是干净的 main。
- 同一时间，`codex/engineering-core` 分支上躺着两个后端大提交：`04ffa0f`（多智能体自愈状态机）和 `08fb2e5`（任务队列 + 模型治理，事故源头就是它）。

- 之后这条主线推到 main，Vercel 自动部署，前端和后端就这么**同一次上线**了。

所以不是你改了后端，是两个分支交叉合并之后一起发的。当天 10:44 的 `af7a36a` 也是一条后端改动（改的是 `jobs.py`、`storage.py`），同样进了当天的主线。

## 为什么测试没拦住

新增的章节任务测试用的是本地 SQLite 的 `Store`，本地这版**根本不校验身份**；另外一些测试是在同一个线程里手动塞好身份再跑的。也就是说，「后台线程 + 云端身份」这个组合压根没人测。单测全绿，生产照样挂，就是这么来的。

## 已经做了什么

- 代码修复：在两个入口 `generate_section` 和 `create_section_job` 里，**在提交后台任务之前先把当前请求上下文复制一份**，让后台线程在这个上下文里执行模型调用。这样身份和 token 都跟着进线程。这个做法我本地验证过：不修复时后台线程拿到的是 None，修复后能正常拿到身份。
- 加了止血脚本 `scripts/emergency_preset_hotfix.sh`，支持本地自检、线上冒烟、必要时回滚。
- 相关单测跑到 60 passed。

## 还需要跟进的（这次没塞进热修）

这几条不是这次事故的直接原因，但都在同一批改动里，建议排期处理：

1. 生成的异步契约对不上。后端最多同步等 50 秒，超时就回 202 + job_id，但前端拿的是同步结果，没有轮询任务接口，稍微慢一点就会显示「结果为空」。
2. Vercel 是 Serverless，函数返回后后台线程可能被冻结；任务库又落在临时盘 `/tmp`，跨请求查不到。长期看后台任务在 Serverless 上不太可靠。
3. 每个章节现在都会跑 Draft→Critic→自愈闭环，模型调用次数变多，耗时和费用都上去了。
4. 结构化输出用了 `response_format: json_schema`，个别 OpenAI 兼容网关可能会拒，需要加能力探测或降级。
